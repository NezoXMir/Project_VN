# Этап 07 — Rule-based система рекомендаций

## Цель

Анализировать состояние пользователя по набору правил и показывать
персонализированные подсказки на дашборде. 7 правил мониторят
типичные проблемные паттерны в постановке целей: просрочки,
заброшенные цели, отсутствие плана, перегруз. Один из них
(серия активности) — позитивный, чтобы поощрять прогресс. Все
правила работают на актуальных данных без сохранения в БД —
пересчитываются на каждый рендер дашборда (это не ML, дешёвая
операция).

## Архитектура

`RecommendationService::generate(int $userId): array` — единственный
публичный метод. Внутри — 7 приватных правил-методов
`check<Rule>()`, каждое возвращает `?array` (`null` если не
сработало, иначе DTO рекомендации).

DTO рекомендации:
```php
[
    'type' => 'overdue_deadlines',         // машинный код для группировки
    'severity' => 'danger|warning|info',   // визуальный приоритет
    'title' => 'Просроченные дедлайны',
    'message' => 'Цель «...» просрочена. ...',
    'action_url' => '/goals',              // куда вести
    'action_label' => 'К целям',           // текст кнопки
]
```

Правила выполняются в порядке `danger → warning → info` — рендер
во вью этот порядок сохраняет, поэтому самое важное всегда сверху.

**Без интерфейсов и абстрактных классов.** 7 методов в одном
сервисе — самое читаемое решение для текущего масштаба. Если
правил станет 15+, имеет смысл вынести в `App\Services\Rules\*Rule`
с общим интерфейсом — но сейчас это преждевременная абстракция.

## Семь правил

### 1. OverdueDeadlines (danger)

**Триггер:** хотя бы одна активная цель с `deadline < сегодня`.

**Сообщение:**
- 1 цель: «Цель «X» просрочена. Перенесите дедлайн или завершите задачи.»
- N целей: «У вас N целей с просроченным дедлайном. Перенесите даты или завершите задачи.»

### 2. UpcomingDeadlines (warning)

**Триггер:** активная цель с `deadline ∈ [сегодня, сегодня+3 дня]`.

**Сообщение:**
- 1 цель: «До дедлайна цели «X» — {DateHelper::timeLeftLabel}.»
- N целей: «У N целей дедлайн в ближайшие 3 дня.»

### 3. LowProgress (warning)

**Триггер:** активная цель, созданная больше 14 дней назад, с
прогрессом < 30%.

**Сообщение:** «N {целей} {висит/висят} больше 2 недель с
прогрессом ниже 30%. Возможно, стоит разбить на меньшие шаги
или пересмотреть подход.»

### 4. Streak (info — поощрение)

**Триггер:** текущая серия ≥ 3 дней подряд с завершёнными задачами.

**Сообщение:** «Вы закрываете задачи N {день/дня/дней} подряд.
Так держать!»

Без `action_url` — это «похвальный пост», не зов к действию.

### 5. NoActivity (danger)

**Триггер:** есть хотя бы одна активная цель И за последние 3 дня
не было ни одной завершённой задачи.

**Сообщение:**
- Если есть исторические задачи: «Последняя завершённая задача —
  {N дней назад}. Закройте одну сегодня — серия начнётся заново.»
- Если ни одной: «У вас есть активные цели, но ни одна задача
  ещё не завершена. Начните с малого — закройте одну подзадачу
  сегодня.»

Это правило взаимоисключающее с #4 Streak: либо ты в простое,
либо в серии.

### 6. EmptyGoals (warning)

**Триггер:** активная цель старше 1 дня без подцелей.

**Сообщение:**
- 1 цель: «Цель «X» не разбита на подцели. Добавьте план — без
  шагов прогресс не считается.»
- N целей: «У N целей нет подцелей. Без плана прогресс не
  считается.»

«Старше 1 дня» — чтобы не дёргать пользователя сразу после
создания цели, у него ещё не было времени её разбить.

### 7. TooManyGoals (warning)

**Триггер:** > 5 активных целей одновременно.

**Сообщение:** «Активных целей: N. Лучше сфокусироваться на
3–4 ключевых — остальные можно отправить в архив, чтобы не
распыляться.»

## Краткое описание ключевых решений

**Один сервис с приватными методами вместо паттерна Strategy.**
Альтернатива — `RuleInterface` и 7 классов, RecommendationEngine
как реестр. Минус — 7 файлов вместо одного на текущем размере,
сложнее искать и читать. Плюс — легче тестировать каждое правило
в изоляции, проще добавлять новые. Решено: один сервис до тех
пор, пока правил ≤ 10. На 15+ — рефакторим в Strategy.

**Один проход по `Goal::with('subtasks.tasks')`.** Все 7 правил
получают одну и ту же коллекцию `$goals` — eager-load делает
3 SQL-запроса (goals + subtasks + tasks) независимо от числа
целей. Без eager-load был бы N+1 в правилах #3 и #6 (проверка
прогресса требует tasks, проверка пустых целей — subtasks).

**Streak считается отдельным запросом.** Технически дубликат
с `StatsService::currentStreak`, но переиспользовать — это
service-to-service зависимость или придётся передавать
streak в `generate()` как параметр (разрывая контракт «дай
userId, получи рекомендации»). Решено: 15 строк дубликата
ради независимости сервиса. Если streak понадобится в третьем
месте — вынесем в `StreakCalculator`.

**Без хранения рекомендаций в БД.** Альтернатива — таблица
`recommendations` с генерацией по cron'у. Минусы: рекомендации
устаревают между запусками, добавляется консистентность
(пометить как «прочитанное», «отклонённое», и т.д.). Для
дипломного проекта — overkill. Текущее решение: рекомендации
живут только во время рендера дашборда, всегда актуальные.

**Severity → цвет фона, не граница.** Альтернатива — белый
фон с цветной рамкой. Цветной фон сильнее визуально привлекает
к проблеме, что важно для предупреждений (danger/warning).
Информационная карточка (info) тоже с цветным фоном для
консистентности.

**Действия — простая ссылка на `/goals`.** Альтернатива —
deep-link на конкретную цель (`/goals/123`). Минус: для правил
с N целями (LowProgress, EmptyGoals при N > 1) у нас N-сценарий
без определённой «главной» цели. Простая ссылка на список —
консистентное поведение во всех случаях.

**Streak = 3 как порог поощрения.** Меньше — ещё не «серия»
(вчера + сегодня = 2 дня — может быть случайностью). Больше
(5+) — слишком высокая планка для нового пользователя. 3 дня —
психологически значимое начало привычки. Если вы 3 дня подряд
закрываете задачи — это уже паттерн, его стоит поощрить.

## Notes (нетривиальные обоснования)

1. **Почему правила-методы возвращают `?array`, а не throw'ят
   при не-срабатывании.** Метод выполняется всегда (нет
   try/catch), при не-срабатывании просто `return null`. Цикл
   `foreach` отфильтровывает null'ы. Минимум ритуала, понятный
   контракт «вход — данные, выход — recommendation или null».

2. **Почему массив сообщений не вынесен в `lang/ru.php`.**
   Стандартный подход Laravel для i18n — `__('messages.recommendations.overdue')`.
   Минусы: дополнительный слой косвенности, нужно поддерживать
   синхронность ключей. Дипломный проект всегда на русском, и
   сообщения часто включают динамику (имя цели, число) которую
   через lang-keys выражать неуклюже (`__(':count :word с просрочкой', ...)`).
   Inline-сообщения проще читать и менять.

3. **Почему `checkUpcomingDeadlines` использует `DateHelper::timeLeftLabel`,
   а не строит фразу самостоятельно.** `DateHelper` написан для
   подписи дедлайна на `/goals` (Этап 04, доп.) — он уже знает
   правильное склонение «осталась 1 неделя» / «осталось 2 дня».
   Переиспользование экономит мозговое усилие — не надо помнить
   правила склонения дважды. Если в будущем понадобится «через
   2 дня» вместо «осталось 2 дня» — добавим вариант в DateHelper.

4. **Почему #5 NoActivity не использует `streak == 0`.** Streak=0
   значит «сегодня нет активности И вчера тоже нет». Но это
   «короткий простой» — пользователь мог взять day off. NoActivity
   срабатывает на 3 дня без активности — это уже системная
   проблема, заслуживающая флага danger. Разделение даёт более
   точную семантику.

5. **Почему правило #3 LowProgress смотрит на возраст цели
   (≥ 14 дней), а не только на прогресс.** Без age-чека любая
   только что созданная цель с 0% прогресса попадала бы в
   рекомендации — что бессмысленно (пользователь только что
   создал её, она физически не могла прогрессировать). 14 дней —
   разумный порог: «цель не должна висеть на 0–30% полмесяца».

6. **Почему правило #7 TooManyGoals — это warning, а не info.**
   На первый взгляд это «информационное» наблюдение, не
   проблема. Но проект задуман как наставник, и часть его
   ценности — учить фокусу. > 5 целей сильно коррелирует
   с «я сейчас распыляюсь и ни одну не доведу». Поэтому
   warning, а не нейтральный info.
