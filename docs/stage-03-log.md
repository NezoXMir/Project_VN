# Этап 03 — Управление пользователями (Admin)

## Цель

Дать администратору список всех пользователей системы и возможность
переключать роль `user` ↔ `admin` через UI. Реализовать два
бизнес-инварианта на уровне сервиса (а не контроллера или UI):
(а) нельзя менять собственную роль, (б) нельзя понизить
последнего администратора. Обе проверки работают под транзакцией
с `lockForUpdate()`, чтобы исключить race condition при
конкурирующих запросах.

## Выполненные действия

1. Создан `app/Services/UserService.php`:
   - `list(): Collection` — `User::orderByDesc('created_at')->get()`.
   - `changeRole(int $id, string $role, int $actorId): User` —
     ранние валидации (роль из white-list, `$id !== $actorId`),
     далее `DB::transaction` с `lockForUpdate()` на целевом
     пользователе. Если целевой — admin и понижается до user,
     дополнительно блокируется счётчик `User::where('role','admin')`
     с `lockForUpdate()` (см. Notes #1) и проверка
     `<= 1` → `DomainException`. Если новая роль совпадает
     с текущей — возвращаем без UPDATE (без шума в логах БД).
2. Создан `app/Http/Controllers/Admin/UserController.php` (тонкий):
   - `index()` — отдаёт `view('admin.users.index')` с коллекцией
     из `UserService::list()`.
   - `updateRole(Request, int $id)` — валидирует поле `role`
     (`in:user,admin`), вызывает `UserService::changeRole`,
     ловит `DomainException`, рендерит flash через
     `back()->with('error', $e->getMessage())`,
     при успехе — `with('success', ...)`.
3. Создан `resources/views/admin/users/index.blade.php` —
   таблица с колонками: имя (+ метка «(вы)» для собственной
   строки), email, роль (бейдж), дата регистрации (формат
   `d.m.Y`), кнопка действия. Для собственной строки кнопка
   `disabled` с надписью «Нельзя» (UX-уровень защиты,
   дублирующий серверную). Для admin — кнопка «Сделать
   пользователем» (серая), для user — «Сделать админом»
   (индиго). Flash-сообщения `success` (auto-dismiss 4 сек)
   и `error` (auto-dismiss 6 сек) — через Alpine.js.
4. Маршруты в `routes/web.php`:
   - Группа под `middleware(['auth','admin'])` с префиксом
     `admin/` и именованием `admin.`:
     - `GET  /admin/users` → `Admin\UserController@index`
       (`admin.users.index`).
     - `PATCH /admin/users/{id}/role` → `@updateRole`
       (`admin.users.update-role`), `whereNumber('id')`.
5. Обновлён `resources/views/dashboard.blade.php` — для
   админа добавлена кнопка «Пользователи» рядом с «Выйти»
   (через `auth()->user()->isAdmin()`), чтобы зайти в
   /admin/users одним кликом.
6. Smoke-тесты через локальный `php artisan serve`:
   - guest → `/admin/users` → 302 на `/login`.
   - user → `/admin/users` → 403 (RequireAdmin отрабатывает).
   - admin → `/admin/users` → 200, видит обоих пользователей.
   - PATCH user→admin: 302, в БД роль обновилась.
   - PATCH admin (себя) → user: 302, роль НЕ изменилась
     (DomainException → flash error).
   - Прямой вызов `UserService::changeRole($adminId, 'user', $otherId)`
     при единственном admin → `BLOCKED: Нельзя понизить
     последнего администратора.`
   - С двумя админами понижение одного из них работает,
     попытка понизить себя — по-прежнему блокируется.
7. Создан `docs/stage-03-log.md` (этот файл).

## Краткое описание ключевых изменений в коде

**`app/Services/UserService.php::changeRole`** — порядок
проверок выбран так: сначала дешёвые in-memory
(валидация роли, self-check), потом дорогая транзакция.
Это снимает 99% «глупых» запросов до открытия SQL-сессии.
Внутри транзакции `lockForUpdate()` на целевом пользователе
+ отдельный `lockForUpdate()->count()` на admin'ах.
Без блокировки на счётчике возможен сценарий: два
администратора одновременно понижают друг друга, оба
проходят `count() === 2`, оба `UPDATE` — в результате 0
admin'ов. Блокировка строк роли `admin` сериализует
эти транзакции (см. Notes #1).

**`app/Http/Controllers/Admin/UserController.php::updateRole`** —
ловит только `DomainException`, валидационные ошибки
проходят дальше через стандартную Laravel-обработку
(возврат с `errors`). Так разделены два уровня:
валидация формы (Laravel) и бизнес-инварианты
(`DomainException`).

**`resources/views/admin/users/index.blade.php`** — для
собственной строки выводится `<button disabled>` вместо
формы. Это намеренно: чтобы пользователь видел
заблокированную кнопку и понимал, что действие не
разрешено, а не пропадало вообще. Доп. подсветка строки
`bg-indigo-50/40`.

**`routes/web.php`** — группа использует
`prefix('admin')->name('admin.')`. Так в Blade пишется
коротко: `route('admin.users.index')` без длинных
строк. `whereNumber('id')` отсекает 404-уровневые
ошибки до контроллера.

## Как поднять и проверить

```bash
php artisan serve   # http://localhost:8000
# Логинимся как admin@example.com / password
# Открываем /admin/users
```

Smoke-чеклист:

- [ ] Гость открывает `/admin/users` → редирект на `/login`.
- [ ] Залогиненный user открывает `/admin/users` → 403
      «Доступ только для администраторов.».
- [ ] Admin открывает `/admin/users` → видит таблицу со
      всеми пользователями, своя строка подсвечена и
      имеет кнопку `disabled` «Нельзя».
- [ ] Кнопка «Сделать админом» рядом с user → переводит
      его в admin, появляется флеш «Роль пользователя
      user@example.com обновлена.», бейдж становится
      `admin`.
- [ ] Кнопка «Сделать пользователем» рядом с admin
      (если он не последний) → переводит обратно.
- [ ] Если в системе остался ровно один admin — кнопка
      понижения для другого admin (через манипуляцию)
      → flash error «Нельзя понизить последнего
      администратора.», БД не меняется.
- [ ] На дашборде админа есть кнопка «Пользователи»,
      ведущая на /admin/users.

## Notes (нетривиальные обоснования)

1. **Почему `lockForUpdate()` дважды — на целевом
   пользователе и на admin-счётчике, а не один раз
   на пользователе.** Сценарий race condition:
   два админа `A` и `B` параллельно понижают друг друга
   (A → B's row, B → A's row). Если блокируем только
   целевую строку, каждая транзакция блокирует «свою»
   и обе свободно вычисляют `count() = 2`. Обе проходят
   проверку `> 1`, обе делают UPDATE — итого 0 admin.
   Блокировка `where('role','admin')->lockForUpdate()`
   сериализует чтения счётчика: вторая транзакция ждёт
   первую, читает уже `count() = 1` и падает. Цена
   решения — двойной lock в редком sad-path, в обычной
   жизни (понижение одиночного admin без гонки)
   стоимость нулевая.

2. **Почему `DomainException`, а не кастомный класс
   исключения (например, `LastAdminProtectionException`).**
   Дополнительный класс на каждый кейс — оверинжиниринг
   для двух правил. `DomainException` — встроенное PHP-исключение
   с понятной семантикой («нарушение бизнес-правила, не
   технический сбой»). Контроллер ловит его одной строкой,
   тип исключения не нужен для формирования сообщения —
   текст уже в `$e->getMessage()`. Если правил станет
   5+, имеет смысл вынести в иерархию; сейчас — преждевременно.

3. **Почему UI-уровень защиты («Нельзя» disabled-кнопка)
   повторяет серверную проверку, а не доверяет ей одной.**
   Без UI-уровня админ видит активную кнопку, кликает,
   получает flash error — это плохой UX. С disabled-кнопкой
   состояние «нельзя» сразу видно, не надо тратить клик.
   Серверная проверка остаётся единственным надёжным
   гейтом (никто не мешает отправить PATCH через curl
   мимо UI), UI-уровень — только для удобства.

4. **Почему `back()` вместо `redirect()->route(...)`.**
   `back()` сохраняет точное место (с фильтрами, скроллом,
   query-параметрами), куда админ вернётся после действия.
   В нашем случае страница только одна, разница
   незаметна, но если на Этапе 11 добавится
   pagination/filtering, `back()` продолжит работать
   корректно без правок контроллера.

5. **Почему `Route::middleware(['auth','admin'])` (auth
   перед admin), а не наоборот.** Порядок имеет значение:
   `auth` редиректит гостя на /login (302), `admin` для
   гостя выкинет 403. UX-разница большая: гостю важнее
   увидеть форму логина, чем «доступ запрещён». Также
   `admin` middleware вызывает `Auth::user()->isAdmin()`,
   и если пользователя нет, `Auth::user()` вернёт `null`,
   и без `auth`-гейта код выкинет fatal на `null->isAdmin()`.
   Поэтому auth обязан быть первым.
