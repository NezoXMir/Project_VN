# Этап 08 — Достижения и геймификация

## Цель

Внедрить систему из 8 бейджей-достижений, разблокируемых по
действиям пользователя: завершение задач, завершение целей,
поддержание серии активности, создание собственной категории.
Разблокировка проверяется автоматически после ключевых действий
(toggle задачи, complete цели, create категории) и сопровождается
toast-уведомлением через AJAX (для toggle) или flash-сообщением
(для остальных). Виджет на дашборде показывает последние 3
разблокированных бейджа, отдельная страница `/achievements` —
полный список с фильтром «получено / заблокировано».

## Восемь достижений

| # | Бейдж | Иконка | Условие |
|---|-------|--------|---------|
| 1 | Первый шаг | 👶 | Завершена 1 задача |
| 2 | Десятка | 🔟 | Завершено 10 задач |
| 3 | Сотня | 💯 | Завершено 100 задач |
| 4 | Финишёр | 🏁 | Завершена 1 цель |
| 5 | Пятёрка целей | 🏆 | Завершено 5 целей |
| 6 | Неделя огня | 🔥 | Серия 7 дней с задачами |
| 7 | Месяц фокуса | 🎯 | Серия 30 дней с задачами |
| 8 | Свой стиль | 🎨 | Создана собственная категория |

Три бакета: объём (1, 2, 3), завершённость (4, 5), консистентность
(6, 7) — плюс один за персонализацию (8). Сбалансировано так,
чтобы новичок получил пару бейджей в первый же день («Первый
шаг» + «Свой стиль» при первом редактировании категорий), а
дальше открывал всё более редкие.

## Архитектура

### Схема БД

- **`achievements`** — справочник из 8 системных записей (вставлены
  прямо в миграцию, как и категории в Этапе 04). Поля:
  `code` (unique, для логики), `name`, `description`, `icon`
  (emoji-string), `threshold` (int, для UI/сортировки),
  `sort_order` (int, порядок отображения).

- **`user_achievements`** — pivot-таблица: `user_id`,
  `achievement_id`, `unlocked_at`. Уникальный композитный
  индекс `(user_id, achievement_id)` гарантирует идемпотентность
  на уровне БД (повторный insert не создаст дубликат).
  FK CASCADE с обеих сторон — удаление пользователя или
  достижения чистит pivot.

### Сервис

`app/Services/AchievementService.php` — единственный
публичный метод `check(int $userId): array`. Внутри:

1. Загружает уже разблокированные коды одной выборкой.
2. Прогоняет 8 правил-замыканий, пропуская уже разблокированные.
3. На сработавших правилах — insert в `user_achievements` с
   `unlocked_at = now()`.
4. Возвращает массив только что разблокированных
   `Achievement`-моделей (для toast/flash).

Каждое правило — приватный метод `checkXxx()`, возвращает `bool`.
Этот же паттерн использовался в `RecommendationService` (Этап 07).

### Хуки

Контроллеры (а не сервисы) дёргают `AchievementService::check`
после ключевых действий — это держит сервисы single-purpose,
оркестрация остаётся в HTTP-слое:

- **`TaskController::toggle`** — проверка только при переходе
  в `is_done = true` (снятие галочки не должно перезапускать
  правила: достижения не «откатываются»).
- **`GoalController::complete`** — после смены статуса на
  `completed`.
- **`CategoryController::store`** — после создания категории.

### Доставка пользователю

| Действие | Способ | Где видно |
|----------|--------|-----------|
| Toggle задачи (AJAX) | JSON-поле `unlocked_achievements` в ответе | Toast в правом верхнем углу `/goals/{id}`, auto-dismiss 6 сек |
| Complete цели | append к flash `success` | Зелёный banner на `/goals/{id}` |
| Create категории | append к flash `success` | Зелёный banner на `/categories` |
| Автоматически (любые невидимые) | — | Виджет «Последние достижения» на `/dashboard`, полный список на `/achievements` |

12. **Навигация и обзорный прогресс (доб. итерация).** После
    первого прохода обнаружилось: при срабатывании toast-уведомления
    пользователь видит «получил достижение», но не понимает, где
    смотреть полный список. Поэтому:
    - В шапку дашборда добавлена прямая кнопка «Достижения» →

      первого экрана.
    - На странице `/achievements` под каждой заблокированной
      карточкой добавлен мини-прогресс-бар вида «3 / 10» с
      процентами. Это отвечает на вопрос «насколько я близок».
    - В `AchievementService` добавлен публичный метод
      `progressFor(int $userId): array` — возвращает
      `[code => ['current', 'threshold', 'percent']]` для всех
      8 правил. `current` ограничен `threshold` (нет смысла
      показывать «150 / 100»).
    - `checkStreak` отрефакторен на `currentStreak` + сравнение
      с порогом — оба места теперь используют один helper.

## Краткое описание ключевых решений

**Системные достижения вставляются в миграцию, не сидером.**
8 записей — часть схемы, без них приложение работает некорректно
(сервис ожидает их `code`). Тот же паттерн, что и для системных
категорий в Этапе 04.

**Хуки в контроллерах, не в сервисах.** Альтернатива — `TaskService::toggle`
сам бы вызывал `AchievementService::check`. Минус — service-to-service
зависимость, сложнее тестировать toggle в изоляции, плюс смешивание
ответственностей (TaskService должен только переключать чекбокс,
не знать про мета-систему достижений). Контроллер как оркестратор —
правильный слой.

**`check()` идемпотентен на двух уровнях.** На уровне SQL —
unique-индекс `(user_id, achievement_id)` блокирует дублирование.
На уровне сервиса — pre-load уже разблокированных кодов и `continue`
для них. Это ускоряет path «уже всё разблокировано» (типичный
случай для активного юзера) до одной выборки.

**Toast — только для toggle (AJAX).** Для goal complete /
category create уже работает flash-механизм, и добавлять полноценный
toast-стек туда — лишний JS. Append к flash-message с эмодзи
(«Получено достижение: 🏁 Финишёр») даёт похожий visual cue
без дополнительной инфраструктуры.

**Toggle проверяет достижения только при переходе в done.**
Снятие галочки (is_done false → true → false) не должно
перезапускать правила. Достижения за «10 задач» не теряются
если вы расчекнули задачу — это было бы плохой механикой
геймификации (наказание за исправление ошибки).

**`streak_7` и `streak_30` — отдельные правила, не одно с порогом.**
Альтернатива — одно правило с массивом порогов, разблокирующее
ту достижку, которая достигнута. Минус — пришлось бы хранить
текущий «уровень streak» где-то ещё. С двумя независимыми
правилами всё работает через тот же `check()` без специальной
логики.

**Серия (streak) считается тут заново, не делегируется
StatsService.** Тот же кусок логики уже живёт в `StatsService`
и `RecommendationService` — третий раз. Можно было вынести в
`StreakCalculator`, но 15 строк дубля проще, чем service с одним
методом. Если придётся менять алгоритм — три места против одного
не критично, тестами поймаем рассинхрон.

**`unlocked_at` хранится отдельно от `created_at` pivot'а.**
Альтернатива — использовать `created_at` (Laravel `withTimestamps`).
Минус — `created_at` семантически про «когда создана связь в БД»,
не «когда юзер заслужил достижение». Для большинства кейсов это
одно и то же, но если в будущем понадобится backfill старых
данных (импорт, миграция), `unlocked_at` останется правильной
датой. Цена — одна лишняя колонка timestamp.

## Notes (нетривиальные обоснования)

1. **Почему `code` — отдельное строковое поле, а не используем `id`.**
   `id` — числовой PK, может поменяться при миграции/реимпорте.
   `code` — стабильный человекочитаемый идентификатор
   (`'first_task'`), на него опирается логика сервиса. Если
   понадобится seeder заново или fresh миграция — id новые,
   но код тот же, и связь с правилами не сломается.

2. **Почему `belongsToMany` с pivot, а не `hasMany` через `UserAchievement` модель.**
   `belongsToMany` со встроенным pivot — короче в коде и в SQL.
   Полноценная Eloquent-модель `UserAchievement` нужна была
   бы только если бы pivot имел сложную логику (методы,
   accessors). У нас pivot — это просто связь + дата
   разблокировки, для этого достаточно `withPivot('unlocked_at')`.

3. **Почему `streak_7` срабатывает ровно на пороге 7, не «когда серия впервые ≥ 7».**
   Это одно и то же на практике. Когда серия дойдёт до 7 ровно,
   `check()` сработает и разблокирует. На 8-м дне правило
   пропустится (уже разблокировано). На 30-м дне сработает
   `streak_30`. Никаких лишних insert'ов.

4. **Почему flash-сообщение для goal complete / category create
   просто append'ится к существующему `success`, а не идёт
   отдельным `unlocked_achievement` ключом.**
   Альтернатива — отдельный flash key и отдельный визуальный
   блок наверху. Минусы: два уведомления вместо одного, нужна
   правка layout'а во всех местах. Append к существующему
   success даёт один баннер с двумя плотно связанными новостями
   («что сделано» + «что получено за это»).

5. **Почему toast — только на `/goals/{id}`, не глобально в layout.**
   Toast'ы нужны только тогда, когда ответ приходит по AJAX
   (toggle задачи). Все остальные действия используют form-submit
   с redirect → flash. Глобальный toast-стек в `layouts/app.blade.php`
   потребовал бы отдельной системы получения данных (custom
   header, JSON endpoint), что overkill для одного источника
   событий. Toast живёт в `goals/show` рядом со своим триггером.

6. **Почему виджет на дашборде показывает 3 последних, а не
   например «5 закрепленных за месяц».** 3 — компактно по
   ширине (3 колонки на md+), плюс самые свежие — самая
   эмоциональная связь. Если пользователь хочет всю историю —
   ссылка «Все →» рядом с заголовком ведёт на `/achievements`.

7. **Почему правила-замыкания, а не `match` + методы.**
   Замыкания дают lazy-evaluation: правило выполняется только
   если оно ещё не разблокировано. С `match` пришлось бы
   сначала вычислять условие, потом проверять разблокировано
   ли оно — лишняя работа на повторных вызовах. Сейчас на
   activeUser'е (все 8 разблокированы) `check()` делает
   только одну выборку из user_achievements и не вызывает
   ни одной проверки.
