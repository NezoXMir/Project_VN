# Этап 06 — Дашборд и мониторинг прогресса

## Цель

Превратить заглушку `/dashboard` («Аккаунт активен. Роль: user.»)
в полноценную панель пользователя: KPI-карточки с ключевыми
метриками, общий прогресс по всем задачам, график активности
за 30 дней (Chart.js), список ближайших дедлайнов с цветовой
индикацией. Все агрегации считаются в одном сервисе
(`StatsService`), контроллер тонкий и не делает запросов к БД
напрямую.

## Выполненные действия

### A. StatsService

1. Создан `app/Services/StatsService.php` — единый источник
   агрегатов для дашборда:
   - **`dashboard(int $userId): array`** — публичный метод,
     возвращает массив со всеми метриками. Контроллер вызывает
     один раз и передаёт во вью.
   - **`currentStreak(int $userId): int`** — серия подряд идущих
     дней с хотя бы одной завершённой задачей. Алгоритм: тянем
     `DISTINCT DATE(completed_at)` по задачам пользователя,
     кладём в `array_flip` (set), стартуем курсор от `today` (или
     `yesterday`, если сегодня пусто — серия может «висеть» на
     вчерашнем дне), идём назад пока день есть в set'е.
   - **`activity(int $userId, int $days): array`** — массив
     `[{date, count}, ...]` длиной `$days`, заполненный нулями
     для дней без активности. Один SQL-запрос
     `GROUP BY DATE(completed_at)`, потом маппинг в плотный
     массив дат — нужен ровный график, без «прыжков» по
     дням-пробелам.
   - **`upcomingDeadlines(Collection $goals, int $daysAhead):
     Collection`** — берёт уже загруженную коллекцию целей
     (без отдельного SQL), фильтрует активные с дедлайном ≤
     `today + $daysAhead`, сортирует по `deadline`. Включает
     просроченные (для подсветки красным).

### B. DashboardController

2. Создан `app/Http/Controllers/DashboardController.php`:
   единственный метод `index()`, инжект `StatsService`,
   передача всего snapshot'а в массиве `stats` во вью
   `dashboard`.
3. В `routes/web.php`:
   - Импорт `DashboardController`.
   - `Route::view('/dashboard', 'dashboard')` заменён на
     `Route::get('/dashboard', [DashboardController::class,
     'index'])->name('dashboard')`. Имя роута `dashboard`
     сохранено — все ссылки в проекте продолжают работать.

### C. Дашборд (`resources/views/dashboard.blade.php`)

4. Старая заглушка «Аккаунт активен. Роль: …» удалена.
   На её место — три блока:
   - **Шапка:** приветствие + быстрые кнопки (Мои цели,
     Категории, для admin — Пользователи, и Выйти). Сохранено
     с прошлых этапов.
   - **KPI-карточки** (4 шт., grid 2×2 на мобиле, 1×4 на md+):
     Активные цели (indigo), Завершённые (emerald), Выполнено
     задач X/Y (sky), Серия подряд N дней (amber). Каждая
     карточка — белый бокс с левой цветной полоской
     (`border-l-4 + border-left-color`) и эмодзи-иконкой
     справа. Цвета согласованы с системными категориями.
   - **Полоса общего прогресса** — показывается только если
     есть хотя бы одна задача. `done / total` с анимацией
     500ms.
5. **График активности** (`<canvas id="activityChart">`, Chart.js):
   - Bar-chart, ось X — даты в формате `DD.MM`, Y — количество
     задач. Дни с 0 раскрашены в светло-серый (`#E5E7EB`),
     дни с активностью — индиго (`#4F46E5`). `borderRadius: 4`,
     `maxBarThickness: 24` — компактные столбики, 30 точно
     влезают.
   - Y-ось целочисленная (`stepSize: 1, precision: 0`),
     `suggestedMax: max(counts) + 1` — даёт «воздух» сверху.
   - `responsive: true, maintainAspectRatio: false` —
     контейнер `relative h-64` фиксирует высоту.
   - Tooltip: «N задач(и)» (без правильного склонения для
     простоты — графический контекст).
   - Empty-state: если за 30 дней ноль завершённых задач —
     вместо canvas'а серый текст «Пока нет завершённых задач.
     Откройте цель, разбейте её на подцели и начните
     выполнять — статистика подтянется.».
6. **Ближайшие дедлайны** (правая колонка на lg+):
   - Цветовая индикация по близости: просрочено / `< 3` дней →
     red, `< 7` → amber, остальное → gray. Тон применяется и к
     фону `<li>`, и к цвету текста, и к pill-бейджу справа.
   - В каждом item'е: заголовок цели, цветная пилюля категории
     (через inline-стили из `Etap 04`), дата формата
     `DD.MM.YYYY`, pill справа с подписью «остался 1 день» /
     «осталось 3 дня» / «осталась 1 неделя» (`DateHelper`
     из Этапа 04) или «просрочено».
   - Ссылка на `goals.show` оборачивает item целиком — клик
     ведёт к цели.
   - Empty-state: «На ближайшие 14 дней дедлайнов нет.».

### D. Подключение Chart.js

7. Тег `<script src="...chart.umd.min.js">` уже был в
   `layouts/app.blade.php` ещё с Этапа 01 (см. Notes #2 в
   `stage-01-log.md`) — здесь только используется. Скрипт
   инициализации обёрнут в `@push('scripts')` и условно
   подключается через `@if (collect($stats['activity_30d'])
   ->sum('count') > 0)` — на пустом графике скрипт не
   вызывается, не пытается работать с несуществующим
   `<canvas>`.

## Краткое описание ключевых решений

**Один публичный метод `dashboard()` вместо 5 раздельных
геттеров.** Альтернатива — отдельные методы `getActiveGoals`,
`getStreak`, `getActivity` и т.д., которые контроллер
складывает в массив. Минусы: пять вызовов из контроллера,
пять SQL-запросов вместо одного eager-load по `goals`,
лёгкий разъезд при добавлении новой метрики (надо помнить
поправить и сервис, и контроллер). Один метод — одна
ответственность («собери всё для дашборда»), один проход
по данным, контроллер тривиальный.

**Eager-load `subtasks.tasks` в `dashboard()`.** Все KPI и
общий прогресс считаются в памяти после одной выборки целей.
Без eager-load каждое чтение `$goal->subtasks->flatMap->tasks`
триггерит N+1. С `with('subtasks.tasks')` — три запроса
максимум (`goals`, `subtasks WHERE goal_id IN (...)`, `tasks
WHERE subtask_id IN (...)`).

**Активность за 30 дней — отдельный SQL вместо подсчёта
in-memory.** Можно было бы взять `$tasks` из уже загруженных
`$goals->flatMap...->tasks` и сгруппировать по
`completed_at->toDateString()`. Минус — это ВСЕ задачи
пользователя, включая давно завершённые. Для streak'а это OK
(он по DATE distinct), но для графика 30 дней лучше тащить
из БД ровно нужный диапазон (`WHERE completed_at >= $start`),
особенно когда задач станет сотни. Граница дешёвая: сейчас
один лишний SELECT, потом хорошая масштабируемость.

**Streak считает «вчерашний» день при пустом сегодня.**
Альтернатива — обнулять серию ровно в полночь, если в этот
день ничего не сделано. UX-плохо: пользователь делал задачи
в 23:50, утром просыпается и видит «серия 0». С учётом «вчера
тоже считается» серия удерживается до конца текущего дня —
у пользователя есть весь день, чтобы её продлить. Если не
успел — обнулится завтра.

**Цветовая палитра карточек жёстко прописана в массиве, а не
взята из `CategoryController::PALETTE`.** На дашборде цвета
несут другую семантику (active = indigo, done = emerald,
streak = amber), не связанную с категориями. Если бы делили
с `CategoryController::PALETTE`, любая правка категорийных
пресетов сломала бы дашборд. Маленькая дублирующая константа —
осознанная цена изоляции.

**Empty-state условно скрывает canvas, не просто прячет.**
Альтернатива — всегда рендерить `<canvas>`, скрывать через
CSS `display: none`. Минус — Chart.js всё равно инициализируется,
кидает варнинг про невидимый контейнер, ест ресурсы. Условный
рендер чище: нет данных — нет canvas'а, нет вызова Chart.js.
То же самое для подключения JS-скрипта через `@push`.

**Dashboard — `GET /dashboard` через `DashboardController`,
а не closure в `routes/web.php`.** Closure быстрее писать
для одной строки, но (а) сервис нельзя инжектить через
type-hint в closure без явной разрешалки, (б) если завтра
понадобится middleware/политика на уровне метода, контроллер
готов, closure — нет. Цена контроллера — один файл с одним
методом, выгода — корректная архитектура.

## Notes (нетривиальные обоснования)

1. **Почему `whereHas('subtask.goal', ...)` для streak/activity,
   а не JOIN.** `whereHas` Eloquent компилирует в подзапрос с
   `EXISTS (SELECT ... FROM subtasks JOIN goals WHERE
   goals.user_id = ?)`. JOIN был бы быстрее на больших объёмах,
   но для дипломного проекта (десятки/сотни задач на пользователя)
   разница нулевая. `whereHas` читается «на одном дыхании», а
   ручной JOIN со всеми aliases — длинный SQL-кусок в PHP.

2. **Почему Chart.js, а не что-то лёгкое типа
   ApexCharts/uPlot.** Chart.js уже подключён в layout с
   Этапа 01 (планировался для этого этапа), его API простой и
   документированный. ApexCharts/uPlot быстрее, но Chart.js
   точно хватит для bar-chart на 30 точек, добавление нового
   CDN ради микро-оптимизации — преждевременная оптимизация.
   Bundle-size CDN не важен (Этап 01 Notes #2 — мы не
   bundler'им).

3. **Почему пороги дедлайнов `< 0 / < 3 / < 7 / иначе` и
   именно эти цвета.** Это три уровня срочности, видимые на
   глаз: «горит» (просрочено, < 3), «скоро» (< 7), «есть
   время» (7-14). Четыре уровня размывают визуальный сигнал;
   два — недостаточно (нет разницы между «завтра» и «через
   неделю»). Палитра `red / amber / gray` — стандартный
   светофор без зелёного (зелёный обычно зарезервирован под
   «завершено», а здесь все цели активные).

4. **Почему `daysAhead = 14`, а не 7 или 30.** 7 дней —
   слишком короткий горизонт, на дашборде часто было бы
   пусто. 30 — наоборот размывает чувство срочности (цели на
   месяц вперёд не «горят»). 14 — компромисс: две недели
   вперёд видно всегда, но не больше. Пользователь хочет
   планировать ближайшие 1-2 спринта, не больше.

5. **Почему `streak` считает с 1, а не с 0 («сегодня нет
   активности → streak=0»).** Streak=1 при одном дне с
   активностью — это «один день подряд», что соответствует
   ожиданию пользователя («у меня серия 1 день, завтра будет
   2»). Если бы считали с 0, серия в 1 день показывалась бы
   как «0 дней подряд» — контринтуитивно.

6. **Почему карточка `Серия подряд` имеет суффикс «дней»
   через `trans_choice`, а остальные — нет.** Только у streak
   значение измеряется в единицах с естественным склонением.
   «Активные цели: 5» — без суффикса, потому что заголовок
   уже несёт смысл «X целей». Аналогично «Завершённые: 3»,
   «Выполнено задач: 12 / 16» — самодостаточно. Со streak'ом
   без суффикса было бы «Серия подряд: 3» — двусмысленно
   («3 чего?»).

7. **Почему JS-инициализация графика обёрнута в IIFE
   `(function() { ... })()`.** Альтернатива — голые
   `const data = ..., new Chart(...)` в `<script>`. IIFE
   изолирует переменные `data`, `ctx`, `labels`, `counts`,
   `maxVal` от глобального scope. Без этого если на странице
   когда-нибудь окажется ещё один `data` (например, второй
   виджет статистики) — конфликт имён. Цена IIFE — две
   обёрточные строки, выгода — гарантия изоляции.
