# Этап 10 — UI Polish: дизайн-система и компоненты

## Цель

К десятому этапу разметка вьюх накопила приличное количество
дублирующегося кода: `bg-white rounded-xl shadow-sm border
border-gray-100 p-5` встречалась десятки раз, flash-уведомления
с Alpine `x-init="setTimeout(...)"` копировались в каждой
вьюхе, pill-бейджи писались inline как `inline-flex items-center
px-2 py-0.5 rounded-full ...`. Цель этапа — извлечь повторяемые
паттерны в Blade-компоненты, чтобы:

- любая правка стиля карточки/бейджа применялась во всех вьюхах сразу
- разметка вьюх стала читаемее (видно бизнес-структуру, не
  Tailwind-простыни)
- новые страницы собирались из готовых блоков, а не копи-пастом

Бизнес-логика и поведение **не затрагивались** — этап чисто
рефакторинг разметки.

## Пять компонентов

### `<x-card>` — белая карточка с тенью

`resources/views/components/card.blade.php`. Параметры:
- `padding` (default `p-5`) — позволяет переопределить
  внутренние отступы (`p-4`, `p-6`, `p-8` или `p-0` для
  таблиц с бордерами)
- `accent` (опциональный hex) — добавляет левую цветную
  полоску `border-l-4 + border-left-color: {accent}`. Используется
  для KPI-карточек дашборда, карточек целей в `/goals`, карточки
  цели на `/goals/{id}`

Через `$attributes->class([...])` принимает дополнительные классы
(`mb-6`, `lg:col-span-2`, `max-w-xl`) и сливает их с базовыми.

### `<x-badge>` — pill-бейдж двух режимов

`resources/views/components/badge.blade.php`. Параметры:
- `tone` — стандартная палитра проекта: `indigo` / `emerald` /
  `amber` / `red` / `sky` / `green` / `blue` / `gray`. Каждый тон
  даёт пару `bg-XXX-100 text-XXX-700`
- `color` (hex) — для категорийных бейджей, у которых цвет
  хранится в БД и Tailwind-purger не знает заранее, какие
  классы нужны. Использует inline-стиль
  `background: {color}1A; color: {color}` — приём, который мы
  ввели ещё в Этапе 04 (доп., категории)

Если задан `:color` — игнорирует `:tone` и использует hex.

### `<x-progress-bar>` — анимированная полоса прогресса

`resources/views/components/progress-bar.blade.php`. Параметры:
- `value` (0–100, число) — заполнение в процентах. Клампится
  на границах (отрицательное значение → 0, > 100 → 100)
- `color` (default `#4F46E5`) — цвет заполнения. Hex для
  категорийных полос, иначе системный indigo
- `size` — `sm` (h-1.5), `md` (h-2 default), `lg` (h-3)

Вынесли отдельной директивой потому что полоса со
`transition-all duration-500` — анимация важна для tactile-фидбека
(прогресс плавно меняется при toggle задачи на странице цели).

### `<x-flash-message>` — auto-dismiss flash из сессии

`resources/views/components/flash-message.blade.php`. Параметр
`type` (`success`/`error`/`warning`). Внутри:
- читает `session($type)` — если ничего нет, ничего не рендерит
- цветовая палитра по типу (зелёный / красный / янтарный)
- Alpine `x-data="{ show: true }"` + `x-init="setTimeout(...)"`
- разный таймер: 4 секунды для success, 6 для error
  (ошибку нужно успеть прочитать)

До рефакторинга этот блок дословно копировался в 7 вьюхах.

### `<x-section-header>` — заголовок секции с опциональным action-link

`resources/views/components/section-header.blade.php`. Параметры:
- `title` — текст заголовка `<h2>` (lg + semibold)
- `subtitle` (опциональный) — серый подзаголовок под title
- `<x-slot:action>` — произвольная разметка справа от заголовка
  (ссылка «Все →», кнопка фильтра, и т.д.)

Заменяет постоянный паттерн
`<div class="flex items-center justify-between mb-4"><h2>…</h2><a>…</a></div>`.

## Краткое описание ключевых решений

**Компоненты, не layouts.** Альтернатива — традиционные
Blade-includes (`@include('partials.card')`). Минусы includes:
параметры передаются через массив с риском пропустить, нет
type-safety, scope изолирован хуже. `<x-card>`-компоненты —
современный API Laravel: type-safe `@props`, attribute bag
с merge-стратегиями (`$attributes->class([])`), slot-механика.

**`@props([])` с дефолтами, не parameters в массиве.** Все
параметры компонентов объявлены в начале файла как
`@props(['padding' => 'p-5', 'accent' => null])`. Это
самодокументирующий контракт — открыл файл, сразу видишь
доступные параметры. Альтернатива через `$attributes->get(...)`
работает, но скрывает API.

**`$attributes->class([...])` для merge-классов.** Это позволяет
писать `<x-card class="mb-6">` и получить базовые классы
карточки + `mb-6` собранные вместе. Без merge-механики
пришлось бы дублировать базу в каждом вызове или городить
параметр `class` вручную.

**Pre-purge-friendly classes.** Tailwind JIT-purger удаляет
неиспользуемые классы из bundle. Если бы мы делали
`bg-{tone}-100` через интерполяцию строк, purger пометил
бы все варианты как не используемые. Поэтому в `<x-badge>`
явный `match` с полными классами в каждой ветке —
сохраняет JIT-обнаружение.

**Inline-стили для категорийных цветов.** В `<x-badge :color="...">`
и `<x-progress-bar :color="...">` цвет приходит как hex из БД
(пользовательские категории). Tailwind-классов под произвольные
hex'ы не бывает — используем `style="background-color: ..."`.
Тот же приём, что был во всех предыдущих этапах.

**`<x-flash-message />` без слота.** Альтернатива — слот для
свободного контента. Но flash-сообщения всегда строка из
сессии, дополнительной разметки им не нужно. Без слота
компонент проще: `<x-flash-message type="success" />` —
одна строчка вместо 6.

**Не делал `<x-button>`.** Кнопок в проекте 5+ вариантов
(primary indigo, secondary gray, danger red, disabled, файловые
input'ы). Универсальный компонент с 4–5 параметрами читается
не проще, чем явные Tailwind-классы. Решено: button оставить
inline, потому что вариативность реальная и она вылезла бы
сложным API. Если в Этапе 11 кнопочный паттерн стабилизируется —
выделим тогда.

**Не вытаскивал палитру в `tailwind.config.js`.** Через CDN
Tailwind config не читается без bundler'а. Можно было бы
определить палитру через `<script>tailwind.config = { theme: {
extend: { colors: {...} } } }</script>` в layout, но
имеющиеся стандартные цвета `indigo-600`, `emerald-500`,
`amber-500` подходят, и менять их семантику нет смысла.

```bash
# Все компоненты созданы вручную через Write
# (php artisan make:component делает структуру с PHP-классом,
# для inline-only компонентов это лишний boilerplate)

# Smoke
php artisan serve
# Curl-скрипт проходит по 11 ключевым URL под user и admin
```

## Notes (нетривиальные обоснования)

1. **Почему компоненты класса-only (без PHP-класса в
   `app/View/Components/`).** Все 5 компонентов — чистая
   разметка с props и условиями. Они не нуждаются в
   методах PHP, computed-полях, сложной логике. Чисто
   Blade-компоненты в `resources/views/components/` —
   самый лёгкий путь, без `php artisan make:component`
   генератора.

2. **Почему `<x-flash-message>` сам читает сессию.** Альтернатива —
   принимать `:message="session('success')"` как параметр.
   Минус — каждый вызов на одну строку длиннее, плюс компонент
   уже знает свой `:type` и логика «прочитать конкретный flash»
   связана с типом 1-к-1. Тесная связь оправдана: если хочется
   передать произвольное сообщение — пишется `<div>{{ $msg }}</div>`
   inline без компонента.

3. **Почему `padding` в `<x-card>` — string, не enum.** Можно было
   ограничить значениями `'sm' | 'md' | 'lg'`. Но Tailwind-padding
   гранулярнее (`p-3`, `p-4`, `p-5`, `p-6`, `p-8`, `p-0`),
   и навязывать размерные пресеты — отнимать гибкость без
   выгоды. String с дефолтом `p-5` покрывает 95% случаев,
   остальные 5% задаются явно.

4. **Почему `<x-section-header>` имеет slot для action,
   а не параметры `actionLabel` + `actionUrl`.** В реальности
   action-блоки разные: где-то ссылка, где-то кнопка-форма,
   где-то Alpine-toggle. Slot позволяет вставить любую
   разметку, параметры заставили бы предусмотреть все формы.

5. **Почему `accent` в `<x-card>` — hex, не Tailwind-класс.**
   Правый край палитры — пользовательские категории с
   произвольными hex из color picker. Tailwind-классы не
   покрывают весь color space. Принимая hex, компонент
   универсален и для системных, и для пользовательских
   цветов.

6. **Почему рефакторинг сделан без visual regression tests.**
   Snapshot-тесты HTML — хорошая практика, но требуют
   инфраструктуры (PestPHP + browser snapshots, или
   Playwright). Для дипломного проекта это перебор.
   Smoke-проверка через curl + ручной осмотр в браузере
   достаточен — изменения мелкие и локальные, ломаться
   нечему вне этих границ.

7. **Почему не использовался `view composer` для общих
   данных шапки.** Сейчас навигация (Мои цели / Категории /
   Достижения / bell / админ-панель / профиль) повторяется
   только на двух страницах (dashboard, admin/users
   возвращает на admin/dashboard). Третий случай ещё не возник.
   Если шапка превратится в reusable layout-фрагмент
   на 3-4 страницах — выделим в `<x-app-header>` с
   slot-кнопками и view composer'ом для unread count.
   Сейчас — преждевременно.
