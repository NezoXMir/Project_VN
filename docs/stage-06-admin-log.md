# Этап 06 (доп.) — Админ-дашборд + экспорт отчёта в PDF

## Цель

Дать администратору отдельную страницу `/admin/dashboard` с
системными агрегатами (без персональных данных пользователей)
и возможностью экспорта отчёта в PDF. Изначально планировалось
через библиотеку `barryvdh/laravel-dompdf`, но composer-установка
упёрлась в SSL-проблему на машине пользователя. Перешли на
браузерный `window.print()` с отдельным `@media print` CSS-блоком —
без внешних зависимостей, кросс-платформенно, native-рендер PDF.

## Принцип «без персональных данных»

В `README.md` зафиксировано: «Без доступа к персональным данным
пользователей — только агрегаты». Это ограничение нести через
весь админский стек:

- `AdminStatsService` возвращает только числа и нагрегированные
  метки, никаких `name`, `email`, `id` пользователей или
  `user_id` категорий.
- В таблице «Популярные категории» показывается label/color
  и счётчик целей — без owner'а.
- В KPI «Активных за 30 дней» — только число, не список.
- В отчёте PDF — те же агрегаты, без источника данных по
  конкретным людям.

## Выполненные действия

### A. AdminStatsService

1. Создан `app/Services/AdminStatsService.php` — отдельный сервис,
   не extends `StatsService`. Логика разная: пользовательский —
   для одного `$userId`, админский — system-wide. Общего почти
   ничего, наследование добавило бы запутанности.
2. Публичный метод `dashboard(): array` собирает за один проход
   контроллера:
   - **`users_total`**, **`users_admin`**, **`users_new_30d`** —
     простые `count()` с `where`.
   - **`users_active_30d`** — пользователи с хотя бы одной
     задачей, завершённой в последние 30 дней. Реализовано
     через `whereExists` (см. Notes #1) — один SQL без JOIN'а
     в проекции, EXISTS короткозамкнут.
   - **`goals_active`** / **`goals_completed`** /
     **`goals_archived`** — `selectRaw('status, COUNT(*) as c')
     GROUP BY status`, потом `pluck('c', 'status')`.
   - **`tasks_total`**, **`tasks_done`**,
     **`tasks_completion_rate`** — счётчики по `Task::done()`.
   - **`registrations_30d`** — массив 30 элементов
     `[{date, count}]`, заполненный нулями для дней без новых
     регистраций (для ровного графика).
   - **`top_categories`** — топ-5 по числу целей через
     `LEFT JOIN goals + GROUP BY + ORDER BY COUNT DESC`. Возвращает
     `label/color/is_system/goals_count` — без `id` и
     `user_id`, см. Notes #2.
   - **`generated_at`** — `Carbon::now()`, для шапки PDF-отчёта.

### B. Admin\DashboardController + маршрут

3. Создан `app/Http/Controllers/Admin/DashboardController.php`:
   единственный метод `index()`, инжект `AdminStatsService`,
   рендер `view('admin.dashboard', ['stats' => ...])`.
4. В `routes/web.php`:
   - Импорт `Admin\DashboardController as AdminDashboardController`.
   - Внутри уже существующей группы
     `middleware('admin')->prefix('admin')->name('admin.')`
     добавлен маршрут `GET /dashboard` → `admin.dashboard`.
     Маршруты `/admin/users` и `/admin/users/{id}/role`
     остались без изменений.

### C. HTML-вью (`admin/dashboard.blade.php`)

5. Шапка отчёта (видна только при печати, через
   `hidden print:block`): «Отчёт по системе X» + дата
   генерации + кто сформировал. Нужна для распечатанного
   PDF — без неё непонятно, что это за документ.
6. Шапка экранная (`no-print`): заголовок «Админ-панель» +
   подзаголовок «Системная статистика — только агрегаты,
   без персональных данных», три кнопки справа:
   - «← Мой дашборд» → `/dashboard` (личный)
   - «Пользователи» → `/admin/users`
   - «🖨️ Экспорт в PDF» — `<button onclick="window.print()">`,
     primary-стиль (indigo).
7. **KPI-карточки** (4 шт., grid 2×2 / 4×1): Пользователи
   (всего + админов), Активные за 30 дней (+ новых),
   Всего целей (+ активных), Задач выполнено (X/Y + %).
   Иконки эмодзи скрываются при печати (бессмысленны
   на бумаге).
8. **Распределение целей** — горизонтальный stacked-bar:
   индиго / зелёный / серый — активные / завершённые /
   архив. Под ним легенда с цифрами. На пустой системе
   (0 целей) — текстовая заглушка.
9. **Регистрации за 30 дней** — Chart.js bar-chart
   (зелёный для дней с регистрациями, светло-серый для
   пустых). Под графиком скрытая на экране таблица
   `<table class="hidden print:table">` — список дат и
   количеств для надёжности печати (см. Notes #3).
10. **Популярные категории** — топ-5 списком, цветной
    кружок + label + счётчик. Метка «сист.» для системных
    категорий — только на экране, при печати скрыта.
11. Подвал отчёта (только при печати): «Отчёт сгенерирован
    системой X. Содержит только агрегированные данные.»

### D. `@media print` CSS

12. Стили положены в `@push('head')` (layout уже поддерживает
    `@stack('head')` ещё с Этапа 01):
    ```css
    @media print {
        body { background: white !important; }
        .no-print { display: none !important; }
        .print-card {
            box-shadow: none !important;
            border: 1px solid #d1d5db !important;
            page-break-inside: avoid;
        }
        .print-grid-4 {
            display: grid !important;
            grid-template-columns: repeat(4, minmax(0, 1fr)) !important;
            gap: 0.75rem !important;
        }
        .print-chart { height: 200px !important; }
        @page { margin: 1.5cm; size: A4; }
    }
    ```
13. Классы:
    - `.no-print` — на навигации, кнопках действий, эмодзи-иконках,
      метках типа «сист.».
    - `.print-card` — на каждом блоке (KPI / распределение /
      графике / категориях). Снимает Tailwind-shadow (печатается
      грязным пятном), фиксирует тонкую серую рамку,
      `page-break-inside: avoid` — карточка не режется поперёк
      страницы.
    - `.print-grid-4` — KPI grid: на экране Tailwind делает
      `md:grid-cols-4`, при печати медиа-query узнает `print`,
      но не размер, поэтому форсим 4 колонки явно.
    - `.print-chart` — высота canvas'а на печати, иначе
      `h-64` (16rem) при 96dpi → ~256px, теряется контекст.
14. `hidden print:block` (Tailwind utility) для шапки и подвала
    отчёта — «не показывать на экране, показывать на печати».
    `hidden print:table` — для резервной таблицы графика.

### E. Навигация

15. На `/dashboard` (личный) кнопка «Пользователи» заменена
    на «Админ-панель» → `/admin/dashboard`. Через админ-панель
    дальше можно перейти на `/admin/users`.
16. На `/admin/users` ссылка «← Дашборд» (вела на личный
    `/dashboard`) переведена на «← Админ-панель» →
    `/admin/dashboard`. Логично: `/admin/users` — это
    sub-page админки, а её «родитель» теперь `/admin/dashboard`.

## Краткое описание ключевых решений

**Почему `window.print()`, а не dompdf.** Изначальный план был
через `barryvdh/laravel-dompdf` (популярная PHP-библиотека для
PDF), но `composer require` упёрся в SSL-цепочку (curl error 60
— self-signed certificate). Это локальная инфра-проблема машины,
не проекта. Альтернативы:
- Чинить SSL — выходит за scope проекта.
- Перейти на mPDF — та же проблема (composer).
- **Браузерный print** — никаких composer-зависимостей,
  native-рендер, выглядит лучше dompdf (который не поддерживает
  flex/grid и современный CSS).
Минус один: пользователь делает один лишний клик в системном
диалоге печати, чтобы выбрать «Сохранить как PDF». Для дипломного
проекта это приемлемая цена за zero-dependency решение.

**Отдельный `AdminStatsService`, не наследник `StatsService`.**
У них разная семантика: `StatsService::dashboard($userId)` —
agregaты для одного человека (его цели/задачи/streak),
`AdminStatsService::dashboard()` — system-wide (всех пользователей,
всех категорий). Общего кода почти нет (разве что паттерн
формирования массива дат для графика — но он в 5 строк).
Наследование добавило бы false abstraction.

**`whereExists` для «Активных за 30 дней», не `whereHas`.**
`whereHas('goals.subtasks.tasks', ...)` создал бы три уровня
вложенных подзапросов с дополнительными `EXISTS`. `whereExists`
с явным JOIN — один subquery, MySQL может его лучше
оптимизировать. На небольших объёмах разницы нет, но
смысловая разница важна: `whereExists` явно показывает,
что мы проверяем существование, не вытаскиваем связь.

**Резервная таблица для печати графика.** Browser print API
обрабатывает `<canvas>` непредсказуемо: некоторые браузеры
снимают bitmap, некоторые рендерят PostScript-картинку,
некоторые показывают пустоту. Чтобы PDF гарантированно
содержал данные регистраций, под canvas'ом лежит таблица
с `class="hidden print:table"` — на экране её нет, при печати
она появляется. Двойная защита.

**`page-break-inside: avoid` на каждой карточке.** Без
этого браузер режет большие блоки (например, секцию с
регистрациями) по разрыву страницы — половина графика на
первом листе, половина на втором. С `avoid` блок целиком
переезжает на следующую страницу, если не помещается на
текущую.

**`@page { margin: 1.5cm; size: A4; }`** — фиксированный
формат и поля. Без этого print диалог использует системные
дефолты (могут быть Letter, могут быть огромные поля, может
не быть полей вообще). Фиксация даёт консистентный отчёт
независимо от платформы.

## Notes (нетривиальные обоснования)

1. **Почему `whereExists` со ссылкой `whereColumn`, а не
   `whereHas`.** `whereHas` Eloquent — удобный сахар, но
   для трёхуровневой связи (User → Goals → Subtasks → Tasks)
   он генерирует три вложенных EXISTS-subquery. Раскрытый
   вариант через `whereExists` с явным JOIN'ом из `tasks`
   через `subtasks` к `goals.user_id` — один subquery с двумя
   JOIN'ами. На больших объёмах MySQL умеет лучше оптимизировать
   простой JOIN, чем серию вложенных EXISTS.

2. **Почему top_categories возвращает label/color/is_system/count,
   а не `id` или `user_id`.** Это **сознательное** ограничение
   ради принципа «без персональных данных». С `user_id` админ
   мог бы определить, чьи категории популярны (через сопоставление
   с `/admin/users`). С `id` (PK) — теоретически тот же leak
   через прямые SQL-запросы. Возвращаем только агрегатные поля,
   которые не идентифицируют ни конкретного пользователя, ни
   конкретную категорию из его коллекции.

3. **Почему резервная таблица под canvas'ом, а не вместо
   него.** Можно было бы при `@media print` скрывать canvas
   и показывать только таблицу. Но canvas — это всё-таки
   визуально информативнее (видно тренд). Браузеры обычно
   успешно конвертируют canvas в bitmap при печати, поэтому
   таблица — это страховка для редких случаев (старые
   версии Firefox, экзотические PDF-принтеры).

4. **Почему shorthand `Carbon::today()`, а не `now()->startOfDay()`.**
   `today()` — статический фабричный метод, читается за один
   взгляд: «сегодня». `now()->startOfDay()` — два вызова и
   менталь-парсинг, что метод значит «обнулить часы». Семантика
   идентичная.

5. **Почему `@push('head')` для CSS, а не `<style>` в `@section`.**
   `@push` к `@stack('head')` (объявлен в `layouts/app.blade.php`
   с Этапа 01) гарантирует, что стили попадут в `<head>`,
   не в `<body>`. Inline `<style>` в `@section('content')`
   технически работает, но валидаторы HTML и SEO-tools
   ругают.

6. **Почему `users_active_30d` — пользователи, выполнившие
   хотя бы одну задачу, а не залогинившиеся.** «Залогинился»
   — слабый сигнал активности (открыл и закрыл). «Выполнил
   задачу» — реальная вовлечённость в продукт. Для админ-метрики
   важнее. Сессии Laravel хранятся в таблице `sessions` (с
   обнулением по TTL), но интерпретировать «активность» через
   них — неточно. Через `tasks.completed_at` — точно.

7. **Почему PDF-отчёт включает только агрегаты текущего
   момента, без исторической глубины.** Дашборд — это snapshot
   «сейчас». Если нужна динамика (например, графики «как
   менялась статистика по месяцам»), это уже не дашборд, а
   reporting. Reporting-функционал может появиться в Этапе 12,
   когда будет полный demo-API; здесь хватает текущей картины
   с подсветкой регистраций за 30 дней (для ощущения роста).
